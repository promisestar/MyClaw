## 1. 项目定位

MyClaw 是一个**个性化 AI Agent 助手**，类似于 Cursor 或 WorkBuddy，但更专注于"理解用户"和"长期伴随"。它能够：

- 在多个项目工作区之间自由切换，隔离不同项目的上下文
- 根据用户选择的模式（Ask/Plan/Craft）自动调整工具权限和交互流程
- 记住用户的偏好、技术栈、代码风格，对话越久越懂你
- 按计划分步执行复杂任务，每一步都可见、可确认

MyClaw 基于开源框架 Hello-Agents 构建，后端使用 Python/FastAPI，前端使用 Vue 3/Ant Design Vue。

## 2. 总体架构

### 目录层级

```
~/.helloclaw/                      # Agent 基座（全局，不随工作区变化）
├── identity/                      #   IDENTITY.md 人格定义
│   └── USER.md                    #   用户画像（对话中自动聚合）
├── config.json                    #   LLM / MCP 全局配置
├── sessions/                      #   会话历史（所有工作区共享）
├── tasks/                         #   任务追踪与计划暂存（所有工作区共享）
├── skills/                        #   全局 Skill（所有工作区共享）
└── workspaces.json                #   已授权的工作区白名单

<workspace>/                       # 工作区（可运行时切换）
└── .myclaw/
    ├── AGENTS.md                  #   项目级行为规范（叠加到人格之上）
    ├── HEARTBEAT.md               #   项目上下文（每轮对话前自动读取）
    ├── uploads/                   #   上传的文件
    ├── skills/                    #   项目专有 Skill
    └── automations/               #   定时任务定义
```

**三层解耦设计**：
| 层级 | 内容 | 随工作区变化？ |
|------|------|:---:|
| 基座 `~/.helloclaw/` | 人格、用户画像、全局配置、会话历史 | ✗ 不变 |
| 工作区 `<project>/.myclaw/` | 项目行为规范、文件、Skills、定时任务 | ✓ 切换时重定向 |
| 运行时内存 | Agent 实例、LLM 连接池、工具注册表 | R/W 运行时切换 |

### 进程模型

- 单个 Python 进程运行一个 MyClaw Agent 实例
- 使用全局 `asyncio.Lock` 保证所有请求串行处理
- 工作区切换时 `bind_workspace()` 全量重绑引用点，无需重启进程
- 切换开销：毫秒级（仅文件系统 setattr 操作）

## 3. 多工作区隔离

### 设计动机

软件工程师通常同时参与多个项目。传统做法是为每个项目启动一个 Agent 进程，但这导致：
- 人格配置需要在每个项目中重复维护
- 用户画像（偏好、习惯）无法跨项目积累
- 进程资源浪费（多个 LLM 连接池、tokenizer 实例）

### 实现思路

MyClaw 将"灵魂"（身份、人格、用户画像）和"工位"（项目文件、项目规范）**彻底分离**：

1. **基座层**：`~/.helloclaw/` 存放永不随工作区变化的内容（人格、画像、全局配置）
2. **工作区层**：`<project>/.myclaw/` 存放项目专属内容（项目行为规范、上传文件、项目 Skills）
3. **切换机制**：`bind_workspace()` 不销毁 Agent 实例，而是通过运行时 setattr 更新文件工具根目录、Skill 目录、浏览器上传目录等引用点

### 最终效果

- 前端下拉框一键切换工作区，无需重启服务
- 切换后身份不变、项目行为规范自动更新为当前项目的
- 会话历史**跨工作区共享**（存储在 `~/.helloclaw/sessions/`），切项目不丢对话
- Shell 命令被限制在当前工作区根目录内，防止跨工作区访问

## 4. Agent 三模式与 Plan 两阶段执行

### 设计动机

传统 AI Agent 只有"全自动"一种模式——看到任务就直接调用工具执行。但实际使用场景有很大差异：
- 有时用户只想查资料，不希望 Agent 擅自改文件
- 有时用户想先看 Agent 的计划，确认后再动手
- 有时用户完全信任 Agent，希望全自动完成

如果让 Agent 自己判断用哪种模式，很容易误判——正则分类无法 100% 准确，而误判比不分类更糟。

### 实现思路

**三种模式定义**：

| 模式 | 触发场景 | 工具权限 | 交互流程 |
|------|---------|---------|---------|
| **Ask** | 概念咨询、代码解释 | 只读（Read/Search/Web/RAG/Memory 检索/`session_search`） | 直接回复 |
| **Plan** | 复杂任务需要确认 | 规划期只读 / 执行期全部 | 生成计划 → 用户确认 → 执行 |
| **Craft** | 全自动编程 | 全部工具 | 自动 ReAct 循环 |

**Plan 模式的两阶段流程**：

1. **规划期**：Agent 在只读模式下收集信息，分析任务，输出结构化的 TODO JSON（含任务描述、依赖关系、所需工具）
2. **确认**：规划结果以 Markdown 卡片形式展示在前端，用户可确认或取消
3. **执行期**：确认后 Agent 恢复计划，按依赖顺序（DAG 拓扑排序）逐步执行

**模式切换**：前端输入框旁的模式选择器（下拉按钮），用户显式选择，零误判。

### 最终效果

- 用户选了 Ask 模式，Agent 绝对不会偷偷写文件
- Plan 模式下复杂任务自动拆解为 3-10 个可执行步骤，含依赖关系
- 每个步骤完成后自动触发下游任务；步骤失败时自动阻塞所有依赖它的下游
- 用户确认计划后才执行，避免"LLM 脑子一热把项目改坏了"

## 5. 工具系统

### 工具总览

| 类别 | 工具 | 副作用 | 说明 |
|------|------|:---:|------|
| 文件 | Read、Write、Edit | Read 无 / Write/Edit 有 | Read 原生支持 PDF/DOCX/XLSX/PPTX 文本提取 |
| 系统 | Execute Command | 有 | 受工作区白名单限制 |
| 计算 | Calculator | 无 | 精确数学计算 |
| 搜索 | Search Content、Search File、List Dir | 无 | 项目文件搜索 |
| 网络 | Web Search、Web Fetch、HTTP Request | 无 | 网页搜索/抓取/API 调用 |
| 知识 | RAG | 有 | 文档入库与检索 |
| 记忆 | Memory（8 个子工具） | 写入类有 / 检索无 | 记忆增删改查 + 画像聚合触发 |
| 跨会话原文 | session_search | 无 | 历史对话 FTS 检索 / 锚定阅读 / 浏览 |
| 扩展 | Skill、MCP、Browser | 视情况 | 扩展能力 |
| 编排 | SubAgent、Task | 有 | 子代理与任务管理 |

### 流式工具调用提前执行

**设计动机**：传统 Agent 必须等 LLM 完整输出所有文本后再解析工具调用，串行等待浪费大量时间。

**实现思路**：当 LLM 流式输出工具参数时，参数 JSON 完整的那一刻就立即执行，同时继续接收 LLM 后续输出。无需阻塞等待整个流结束。

**最终效果**：多工具调用延迟从"N×(LLM 时间+工具时间)"降到"LLM 时间+最慢工具时间"，约 30% 延迟降低。

### 只读工具并行执行

当 LLM 在一个响应中生成多个只读工具调用（如同时搜索多个文件），这些工具可以安全并行。系统自动根据 `has_side_effects` 元数据分组：无副作用的并行、有副作用的串行。

### 工具调用保护

- **去重**：同一轮中相同工具 + 相同参数只执行一次
- **限量**：单轮最多 5 个工具调用，超出部分自动跳过并通知前端
- **错误分类重试**：区分"可重试"（网络超时、HTTP 5xx）和"不可重试"（文件不存在、权限不足）错误，指数退避 + 随机抖动

## 6. 记忆系统与跨会话原文回忆

### 设计动机

Agent 需要在跨会话时间尺度上记住两类信息：

1. **偏好与事实**（「我喜欢简洁回复」）——表述可变，适合语义向量。  
2. **某次对话的原话与过程**（「上周 Redis 怎么配的？」）——必须可检索到消息原文。

若只有 Memory，过程性细节容易丢；若把整段 transcript 写进 Memory，又会污染事实库并每轮浪费 token。因此采用 **三通道**：Memory（事实）+ Profile（人设）+ Session Recall（原文）。

### 实现思路

**Memory 四层（事实层）**：

1. **自动捕获层**：每轮对话结束，自动从用户消息中提取值得记住的内容（偏好、决策、实体、事实等），分类归档
2. **去重层**：写入时先检查是否已有相同内容（字面去重 + 可选的语义去重），防止重复记忆
3. **检索层**：
   - **被动注入**：每轮对话自动语义检索与当前话题最相关的 3 条记忆，注入系统提示词
   - **主动检索**：Agent 按需调用 `memory_search` 做深度语义检索
4. **遗忘层**：每条记忆有衰减分数，按分类以不同速率衰减。重要信息衰减慢（~70 天），易过时信息衰减快（~23 天）。被检索命中的记忆重置计时器——"用进废退"。

**Session Recall（原文层）**：

- 会话 JSON（`~/.helloclaw/sessions/*.json`）仍是权威原文，并继续服务前端历史回放
- 其上维护可重建的 SQLite 全文索引（`index.db`，优先 FTS5，不可用则 LIKE）
- 保存/删除会话时增量更新索引；启动时空库则后台全量重建
- Agent 通过只读工具 `session_search` 按需检索：关键词发现会话、锚定窗口阅读、列近期会话
- **不**每轮自动把旧对话塞进 system prompt，避免与 Memory top-3 抢 token

**分工**：偏好/事实 → Memory；稳定风格 → `USER.md` 画像；「上次具体怎么说的」→ `session_search`。禁止整段 transcript `memory_add`。

### 最终效果

- 用户在对话中随口说的"我喜欢简洁回复"会自动被捕获为偏好记忆
- 下次开启新对话时，Agent 自动检索到这条偏好，回复更简洁
- 高频回想的记忆持久存在，无人问津的自然消退
- 记忆存储在 Qdrant 向量数据库，支持语义检索而非关键词匹配
- 新会话中可追问历史对话原话（如排障步骤、配置约定），Agent 用 `session_search` 引用旧会话片段并给出会话 ID 提示

## 7. RAG 知识库

### 设计动机

用户有时希望 Agent 基于特定的文档内容回答（如项目需求文档、技术规范），而不是仅依赖 LLM 的通用知识。

### 实现思路

用户将文档加入知识库后，文档被自动分割为若干文本块，通过 embedding 模型转换为向量并存入 Qdrant。当用户提问时，系统从知识库中检索与问题最相似的分块，作为上下文注入给 LLM。

### 最终效果

- 支持 PDF、DOCX、XLSX、PPTX、TXT 等多种格式
- 前端可查看已入库文档列表和分段预览
- 对话中可通过 "打开" 按钮直接跳转到聊天页并指定文档
- 文档通过 `Read` 工具直接读取也有效——Read 工具内置文档格式支持

## 8. Skill 技能系统

### 设计动机

对于重复性的领域流程（如"帮我 review 这段代码"、"按照公司规范格式化这个文件"），每次都用自然语言描述规则太低效。需要一个可复用的"技能模板"机制。

### 实现思路

Skill 是包含领域流程描述的 Markdown 文档（`SKILL.md`），Agent 在对话中可以像调用工具一样调用它。Skill 的 prompt 会被临时注入到当前对话上下文中，指导 Agent 如何完成该场景的任务。

**两层 Skill 目录**：

- **全局 Skills**（`~/.helloclaw/skills/`）：个人常用技能，所有工作区共享
- **项目 Skills**（`<workspace>/.myclaw/skills/`）：项目专属技能，仅当前项目可见

前端支持导入 Skill（本地目录或 Git 仓库）、编辑 Skill 内容、一键安装运行环境。

### 最终效果

- `/code-review` 一键触发代码审查流程，Agent 按 Skill 文档中的规范逐条检查
- 全局 Skill（如个人偏好的 commit message 格式）在所有项目中可用
- 项目 Skill（如公司编码规范）仅在该项目中生效

## 9. SubAgent 子代理与 Task 任务追踪

### 设计动机

当 Agent 需要同时搜索多个文件、抓取多个网页时，所有结果都灌入主对话会迅速占满上下文窗口。需要一个机制让重型子任务在隔离环境中执行，只返回摘要。

### 实现思路

**SubAgent**：主 Agent 作为"领导"，把重型任务（如"搜索所有 Python 文件中的 TODO 注释"）委托给子代理。子代理有独立的上下文（不占用主窗口），只能使用主 Agent 授权的工具白名单，执行完后将结果压缩为 ≤300 字摘要回传。

**Task 系统**：复杂任务被拆解为有依赖关系的步骤（"创建配置文件" → "写函数" → "写测试" → "运行测试"）。每个步骤有明确状态（PENDING → IN_PROGRESS → COMPLETED），前置步骤完成后自动解锁后续步骤，失败则自动阻塞下游。

### 最终效果

- 主对话始终保持精简（只看到决策级别的信息）
- 多个互不依赖的子任务可以并行执行
- 复杂多步骤任务有条不紊推进，不会遗忘或跳步
- 任务进度可通过前端面板实时查看

## 10. MCP 工具集成

### 设计动机

Model Context Protocol（MCP）是一种标准化的工具服务协议。一个 MCP 服务器可能暴露几十个子工具，直接在 Agent 工具列表中注册所有子工具会导致 schema 过长，浪费 Token 并干扰 LLM 判断。

### 实现思路

采用**渐进披露机制**：初始只注册一个"mcp"父工具。LLM 首次调用时，系统才连接 MCP 服务器、获取子工具列表、动态注册到工具注册表。后续轮次中 LLM 可直接调用已披露的子工具。

会话切换时自动清理已披露的子工具，避免跨会话污染。

### 最终效果

- LLM 的工具选择列表始终保持精简
- 需要 MCP 能力时才按需展开，不浪费上下文
- 多会话之间子工具状态隔离

## 11. 用户画像自动聚合

### 设计动机

如果让用户手动填写技术栈、代码风格等偏好，大多数人不会做。但如果 Agent 能自动从对话中学习——"用户每次都喜欢给代码加类型注解"、"用户的工作主要是前端 Vue 开发"——画像就能在不知不觉中建立，让 Agent 越来越懂用户。

### 实现思路

每轮对话结束后，系统检查是否满足触发条件（每 10 轮或偏好记忆超过 20 条），满足时调用轻量 LLM 从记忆系统中的 preference/entity/decision 记忆聚合出结构化画像，写入 `USER.md` 的自动区域。

`USER.md` 分为**手动区域**和**自动区域**（用 HTML 注释标记边界，如 `<!-- AUTO:tech_stack -->`）。聚合器只更新自动区域，手动区域完全不受影响。

### 最终效果

- 技术栈、工作领域、沟通偏好、代码风格四个维度自动维护
- 画像跟随用户而非项目（存于 `~/.helloclaw/identity/USER.md`）
- 画像被自动注入系统提示词，Agent 在每次对话中都能感知
- 平均每轮额外消耗仅 ~200 token，几乎无感知
- LLM 不可用时自动降兜为关键词分类，功能不中断

## 12. 定时任务引擎

### 设计动机

某些任务需要定期自动执行——每天发送项目进度总结、每小时检测服务健康状态。不能每次依赖用户手动触发。

### 实现思路

基于 iCalendar RRULE 标准的调度引擎，支持三种调度类型：

- **一次性** (`once`)：指定时间执行一次
- **间隔** (`interval`)：每隔 N 分钟/小时执行
- **循环** (`rrule`)：标准 RRULE 表达式（如 `FREQ=WEEKLY;BYDAY=MO;BYHOUR=9` 表示每周一上午 9 点）

任务独立运行在后台，使用 Agent 实例执行对话。任务输出可配置为通知、静默执行或日志记录。

### 最终效果

- 前端可视化创建/编辑/删除定时任务
- 启用/禁用一键切换
- 运行历史弹窗查看每次执行的状态和结果
- 工作区级隔离，每个项目有独立的定时任务

## 13. 多模态输入

### 设计动机

很多场景下用户想说的事情一张截图比一段文字更清晰——设计稿截图、错误日志截图、表格数据截图。Agent 需要理解图片内容。

### 实现思路

用户在聊天中直接粘贴或上传图片，系统将图片转换为 base64 编码（大图会经过递进压缩：先降 JPEG 质量再降尺寸），作为 VLM（Vision Language Model）的 `image_url` 参数传给 LLM。

**Token 估算优化**：base64 不入聊天历史，改为路径引用（`@FILE:<abs_path>`），每条图片消息从数 MB 降到 ~250 字节。LLM 调用前即时从磁盘读取还原。

### 最终效果

- 拖拽/粘贴/上传图片，Agent 直接看到并理解
- 大图自动压缩至合理大小，不影响上下文窗口
- 历史文件体积不膨胀（路径引用而非 base64 存储）

---

## 14. 会话管理与会话历史

### 设计动机

AI 编程助手的对话可能持续数小时甚至数天，中间可能切换工作区、编辑历史消息、多次重新生成回复。需要有完善的会话持久化和编辑能力。

### 实现思路

**会话生命周期**：
1. 用户打开页面 → 尝试恢复上次会话，否则创建新会话
2. 每次对话完成后自动保存（同时持久化任务状态）
3. 会话历史以标准消息格式存入 JSON 文件

**消息编辑**：用户编辑某条历史消息后重新发送，系统不是简单删除后续历史，而是将完整历史拆分为"前缀"（该轮之前）+ "新回复" + "后缀"（该轮之后），确保后续有价值的对话完整保留。

**跨工作区共享**：会话历史存储在 `~/.helloclaw/sessions/`（全局目录），不随工作区切换而丢失。

**跨会话原文检索**：同一全局目录上维护 SQLite 全文索引；Agent 可通过 `session_search` 在新会话中检索旧对话原文（与 Memory 事实层分工）。索引失败不影响会话 JSON 保存。

### 最终效果

- 会话列表按时间排列，支持新建、打开、删除
- 编辑历史消息后重新生成，后续对话不丢失
- 切换工作区后会话列表依然完整
- 上下文窗口用量实时显示（进度条，超 80% 变黄、超 95% 变红）
- Agent 可按需回忆历史会话中的具体表述（不依赖是否已写入 Memory）

## 15. 外部通信通道

### 设计动机

Agent 不仅仅通过 Web 前端交互——用户可能在企业微信、飞书、Slack 中收到消息后希望 Agent 自动响应。需要一个外部通信通道让第三方系统接入。

### 实现思路

Bridge 作为 WebSocket 中继层，将外部消息（如飞书 bot 消息）转发到 Agent 后端。Agent 后端监听 WebSocket，收到消息后进入标准对话流程，回复通过 Bridge 回传。

外部消息通过全局 Agent 锁串行处理，与 Web 前端请求不冲突。

### 最终效果

- 飞书 bot 接入后，群聊中 @Agent 即可触发对话
- 回复同样通过群聊消息返回
- 与 Web 前端共用同一个 Agent 实例，共享所有记忆和配置

## 16. 上下文窗口管理

### 设计动机

LLM 的上下文窗口是有限资源（如 128K tokens）。系统提示词、对话历史、工具调用参数、工具输出都在竞争这个窗口。如果不做管理，几次大工具调用后窗口就被占满，不得不丢弃早期的重要对话。

### 实现思路

**三道防线**：

1. **事前（Context Guard）**：工具执行前预判其输出大小。小输出直接执行（`< 2000 tokens`）；中等输出执行后截断；大型输出委托给子代理，主上下文只收摘要。有副作用的工具（Write/Edit/Memory 等）不受委托。

2. **事中（Context Manager）**：对话超过窗口 80% 时自动压缩——保留最近的 10 轮完整对话 + 将早期消息压缩为 LLM 生成的摘要。

3. **事后（条件注入与清理）**：入职引导完成后自动从系统提示词中移除（省 ~800 tokens）；低相关记忆不注入；BOOTSTRAP 完成后自动消失。

### 最终效果

- 长对话不会因窗口耗尽而丢失关键信息
- 大型搜索结果（如 5000+ token 的网页内容）自动委托给子代理，不污染主窗口
- 条件注入确保"每条提示词规则都有退出机制"，不用的规则不占窗口

## 17. 工具调用日志

### 设计动机

Agent 调用了哪些工具、每个工具耗时多少、参数和结果是什么——这些信息对调试 Agent 行为、优化性能、排查错误至关重要。

### 实现思路

每次工具调用自动记录：工具名、参数、结果（截断）、状态（成功/失败/重试）、耗时、重试次数。日志按日期分组存储为文件。

### 最终效果

- 前端按日期查看工具调用日志，点击展开 JSON 详情
- 支持删除旧日志文件
- 便于排查"为什么 Agent 调了这个工具而不是那个"

## 18. Web 前端

### 设计动机

Agent 需要一个友好的交互界面——不仅是聊天，还要能管理配置、查看记忆、切换工作区、编辑 Skill、运行定时任务。

### 实现思路

Vue 3 单页应用，包含 10 个路由页面：

| 页面 | 功能 |
|------|------|
| **聊天** | 核心对话：流式 SSE 回复、工具卡片可视化、三模式切换、Plan 确认、附件上传 |
| **会话** | 会话列表、创建、删除、打开 |
| **技能** | Skill 卡片网格、启用/禁用、导入、编辑 |
| **知识库** | 已入库文档列表、分段查看、删除 |
| **工具日志** | 按日期的工具调用日志 |
| **定时任务** | RRULE 定时任务管理、运行历史 |
| **记忆** | 8 分类筛选、搜索、删除、统计、清理 |
| **配置** | 全局配置文件编辑（IDENTITY/USER/SOUL 等） |
| **健康检查** | LLM/Qdrant/磁盘/内存状态 |
| **技能编辑器** | 全屏编辑 SKILL.md |

**流式对话的核心流程**：

1. 用户发送消息 → 前端 POST 请求开启 SSE 流
2. 后端逐事件推送：文本片段（chunk）、工具调用开始（tool_start）、工具执行结果（tool_finish）、步骤结束等
3. 前端维护"混合消息段列表"——文本段和工具卡片交替排列
4. Vue 响应式系统自动最小化 DOM 更新，不需要重新渲染整条消息

**Plan 交互流程**：

1. Plan 模式发消息 → 后端生成 TODO JSON → SSE 推回
2. 前端渲染为 Markdown TODO 确认卡片
3. 用户点击"确认"→ 新请求以 Craft 模式重新发送，后端恢复计划执行
4. 用户点击"取消"→ 清理状态

### 最终效果

- 流式回复文字和工具调用卡片交错展示，实时滚动
- Markdown 支持代码高亮、表格、任务列表
- 暗色/亮色主题一键切换
- 消息编辑、重新生成、取消生成按钮
- 附件图片/文档缩略预览

## 19. 配置体系

### 配置层级

MyClaw 的配置分为三层：

```
优先级：config.json > .env > 代码默认值

全局配置 (~/.helloclaw/config.json)
├── LLM 配置：model_id、api_key、base_url
├── MCP 配置：servers 列表
├── 记忆配置：自动注入开关、top_k、阈值
├── 跨会话回忆：session_recall.enabled、窗口/limit、CJK fallback 等
└── 工具重试配置：重试次数、指数退避参数

环境变量 (backend/.env)
├── LLM_MODEL_ID、LLM_API_KEY、LLM_BASE_URL
├── BRAVE_API_KEY / TAVILY_API_KEY（网页搜索）
├── EXTERNAL_BRIDGE_*（外部通道）
└── WORKSPACE_PATH

身份配置文件 (~/.helloclaw/identity/)
├── AGENTS.md    — 全局行为规范骨架
├── IDENTITY.md  — Agent 身份认知（名称、角色）
├── USER.md      — 用户画像（手动 + 自动聚合）
├── SOUL.md      — 性格特征（语气、风格）
└── BOOTSTRAP.md — 入职引导（完成后自动消失）

工作区配置文件 (<workspace>/.myclaw/)
├── AGENTS.md    — 项目级行为规范（叠加到全局之上）
└── HEARTBEAT.md — 项目上下文（每轮对话前读取）
```

### 系统提示词的构建

每次对话前，系统从多个配置文件组合出完整提示词：

```
AGENTS.md (工作区优先，基座 fallback)
+ BOOTSTRAP.md (仅入职未完成时注入)
+ IDENTITY.md
+ USER.md
+ SOUL.md
+ 子代理使用指引 (自动注入)
+ 任务管理指引 (自动注入)
+ 长期记忆使用指引 (自动注入)
+ 回忆通道指引 (session_search 启用时静态追加)
+ 相关记忆 top-3 (自动注入)
+ 当前时间
───────────────────────
= 完整 System Prompt
```

> Session Recall **不**把旧对话全文自动注入；仅在工具启用时追加静态分工说明，模型需要原话时再调 `session_search`。
### 热加载

修改任何配置文件后，下一次对话自动生效，无需重启服务。LLM 的 model_id/base_url 变更也会在下次对话前自动检测并重新初始化客户端。
